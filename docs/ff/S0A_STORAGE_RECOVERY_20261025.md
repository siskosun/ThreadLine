# S0a 存储与采纳原型：设计、崩溃点与恢复顺序（2026-10-25）

对应计划第十一章 S0a。实现见 `threadline-extension/evidence-core.js`（纯逻辑：限额校验/单事务写入计划/幂等/投影/导入导出）、`evidence-db.js`（`threadline_evidence_v1` 多 store 事务层）、`evidence-prototype.html|.js`（原型页与计时协议）、`background.js` `EV_*` 处理器（service worker 唯一写者）。测试：`test/evidence-core.test.js`（8 项，含 CAS/回滚/幂等/限额）、`test/evidence-e2e.py`（一次性合成配置上的真实 IndexedDB 探针）。

## 1. 权威方向与写入协议

- 权威库：扩展 origin 的 IndexedDB `threadline_evidence_v1`（stores：`conclusions`/`versions`/`sources`/`links`/`projects`/`operations`）。`projects` 以 `projectId` 为键、`operations`（幂等台账）以 `operationId` 为键，其余以 `id` 为键。
- 写入路径：页面只发 `EV_*` 命令 → `background.js` 在既有 `serialize()` 队列上串行执行：**事务外**完成全部校验与 SHA-256（哈希/模型/文件读取绝不进入事务）→ `evidence-core.plan*` 产出写入计划 → `evidence-db.applyPlan` 在**一个** `readwrite` 事务内：先在事务内重读 `projects` 行做 **CAS**（`evidenceRevision` 必须等于计划的 期望值-1，不等即整体 abort），再写入结论/版本/片段/链接/台账并递增修订、标记投影待办。
- 幂等：`operations` 台账记录 `operationId + requestHash(SHA-256) + 结果`。同 ID 同摘要 → 返回原结果（不产生新行）；同 ID 异摘要 → 拒绝。台账与业务行同事务提交，不存在“台账已写而业务未写”的窗口。
- 投影：摘要只从已提交权威库重算（`projectSummary`：`证据库摘析（只读投影，v<修订>，采纳 n 条）` + 每行≤120 码点、显式 `…（见证据库）` 省略 + 全局 1000 码点硬上限带 `（截断…）` 标注）。S0a 投影落在页面上；chrome.storage 投影与 projectionRevision 待办队列是 S1a 交付。

## 2. 崩溃点表与恢复顺序（无待定项）

编号对照 `evidence-db.applyPlan` 的时序；每行给出崩溃后果与恢复动作。恢复动作全部幂等，且**永不重放**外部操作（采集、模型请求、发送）。

| # | 崩溃点 | 后果 | 恢复动作（幂等） |
| --- | --- | --- | --- |
| C1 | 校验/哈希阶段（事务开启前） | 无任何写入 | 客户端以相同 `operationId` 重发；无台账即全新执行 |
| C2 | 事务已开、CAS 读 `projects` 前后、写入中途（含 put 抛错后显式 abort） | IndexedDB 事务原子回滚：无结论、无台账、修订不变 | 相同 `operationId` 重发即全新执行；`test/evidence-core.test.js` 「crash mid-transaction」以注入 abort 验证零部分写入 |
| C3 | 事务 `oncomplete` 已触发、页面未收到回包（SW 被杀/消息丢失） | 权威库已提交，修订已 +1，操作方看到超时 | 相同 `operationId` 重发 → 台账命中同摘要 → 返回原结果（不重复创建）；这正是台账与业务同事务的原因 |
| C4 | 提交后、投影重算前（S1a：chrome.storage 投影待办未消化） | 权威库新、投影旧 | 只读视图永远直读权威库（本原型即如此）；S1a 启动/读取时按 projectionRevision 幂等重算，显示“已保存，摘要待更新”而非阻塞 |
| C5 | 浏览器整体崩溃/重启 | 同 C2/C3 之一 | 重启后权威库自持久存储恢复；`evidence-e2e.py` 已验证 12 条结论+撤回修订跨完整浏览器重启存活 |
| C6 | 导出/导入中途 | 导出：内存对象丢弃；导入：计划校验（字节/格式/ID 冲突/跨课题归属/版本上限）全部在事务外完成，冲突即拒绝、无部分导入 | 重新导出/重发导入命令（幂等台账同上） |

**恢复顺序**（启动时）：打开权威库 → 校验 `projects` 各行 `evidenceRevision` 与各 store 实际内容一致性（S1a 加对账）→ 重算投影待办 → 恢复页面只读视图。任何“权威库缺失/损坏”必须显式报错，禁止以空库重建覆盖（见 §3-D6）。

## 3. 破坏性路径处置（设计冻结，S1a 实施）

- D1 **旧 decision 编辑封口**：课题一旦存在接管记录，`background.js` 的 `MUTATE`/撤销/批量更新入口拒绝该课题直接 decision 修改（非仅禁用按钮）；首次采纳时旧 decision 转为只读摘要 + `legacy-note`（未验证）标注。无接管记录的旧课题沿用旧编辑。
- D2 **撤回 ≠ 删除**：撤回仅置 `withdrawn` 并保留全部版本/证据/历史（E2E 已验证）。
- D3 **显式删除**：清理扩展管理的原文及副本；墓碑不保留正文；已导出外部文件不可收回，删除确认界面明示。
- D4 **旧备份恢复/导入**：导入先限字节、验格式/哈希/引用、预览条数；ID 冲突、跨课题引用、未来版本拒绝或要求明确处理，不静默覆盖（冲突拒绝已测试）。旧格式只恢复它包含的内容，不清空新库。
- D5 **课题删除 ↔ 证据库**：跨库关系用后台串行 + 持久意图/墓碑 + 幂等对账（S1a 交付），不是与正文的双向合并。
- D6 **证据库缺失**：结论视图/交接读取显式报错；不得以空库重建覆盖兼容摘要。

## 4. 首期默认容量（经探针核验后冻结）

| 限额 | 默认值 | 探针依据 |
| --- | --- | --- |
| 结论正文 | ≤4000 Unicode 码点 | 单测边界 4000/4001 |
| 片段上下文 | 前后各 ≤500 码点；单片段 ≤16 KiB UTF-8 | 单测边界；超限显式报错不静默截断 |
| 片段数/总量 | ≤8 片段、≤64 KiB/结论 | 单测边界 8/9 |
| 课题结论数/版本数 | ≤200 结论、≤50 版本 | 单测 200+1 拒绝；版本上限在导入路径校验 |
| 导入/导出包 | ≤20 MiB UTF-8 JSON，超限明示拒绝 | 计划规则；导出计数含原文片段标志 |
| 摘要投影 | ≤1000 码点，显式截断标注 | 单测 |
| 全库产品预算 | 100 MiB（按字节计），配额失败仍需处理 | `storage.estimate` 探针可用（E2E 已采集）；`persisted` 默认 false，本轮不新增权限、不预设获批 |

E2E 环境 `storage.estimate` 返回可用（usage/quota 字段存在）；真实长期大库的峰值内存与淘汰行为在 S1a 用更大合成数据复测后再动这些数字，任何改动留理由。

## 5. 采纳计时协议结果

12 次有效操作全部完成（12/12 ≥ 11 门限），中位 2–3 ms、P90 3 ms（远低于 30s/60s 门限）。**如实声明**：本计时经自动化通道（Playwright 驱动原型页）执行，反映“操作无需帮助即可完成”与提交链路耗时，不冒充真人手速工效学；真人节奏核验可由所有者随时在原型页点击“复制计时 JSON”复核。计时原始数据随 `evidence-e2e.py` 输出与证据 JSON 记录。

## 6. 工期与风险估算（区间）

- **S1a（持久化与恢复实施）**：投影队列 + projectionRevision + 旧编辑封口 + 备份恢复接入 + 对账。估 **16–28 小时**（协议已在 S0a 落定，主要工作量在 background 封口点与恢复测试；风险：MUTATE/撤销/批量更新入口的遗漏面，逐入口加测试）。
- **S1b（采纳与交接 UI）**：整理/Fork 共用逐条采纳、片段展示、交接预览。估 **12–22 小时**（风险：整理记录→片段绑定的来源编号映射；定位降级路径）。
- **S0b（定位 spike）**：另计 ≤8 小时，独立进行。
- 总体风险：ChatGPT DOM 变化影响采集片段来源定位（S0b 降级路径覆盖）；MV3 SW 生命周期导致的投影延迟（C4 设计已兜底）；超大库性能（S1a 复测）。
