## 无迁移的纯规则（首次离线重放的保守版本）

保持现有 `reviewNeeded` / `pending` 安全状态原样可见。分层只派生任务优先级 `must_review` / `before_use`，不能把未核对关系改成已核对。用户的 `deferred` 是单独持久操作，不是自动预测层。

**试点输入成本**：目前 S3 未完整具备来源核验与交接范围的自动读取；测试时不能把 G* 标注者预先整理的字段免费提供给 B。无法独立核验则填 `unknown` / `null` 并保持 `must_review`；人工核验字段的实际时间应记入 B 臂操作日志与总耗时，A/C 仍应获得同等原始资料。SHA 格式检查不能替代现场输入来源和耗时核验。

**输入**：事件 `triggerEventId`、`changeKind`、已注册边类型、每一影响目标的最短路径/边集合、目标是否已采纳、冻结来源核验状态及当前交接是否引用目标；不能从 G* 的实质标签反推这些输入。对于缺少证据的来源核验、边类型、版本身份、行动用途，一律视为 `unknown`；规则按较严层归类，不凭默认“完整”降级。纯措辞仅当用户已独立确认承接、且规则/版本身份有效时可作为低优先级输入。

**优先级（由高到低，首次匹配）：**

1. `must_review`：上游已撤回；来源缺失/哈希失配或未知（无法证明完整）；任何路径上的已知关键必要前提错误；直接必要前提的实质变动且目标已采纳；或因上游规则不完整而无法安全降级。撤回/损坏即使通过两跳以上也不能被降级。
2. `before_use`：在来源完好、无关键安全事件、有可核验的版本/边证据时，才允许对已经确认的纯措辞、确实有独立登记的背景边或安全的两跳以上间接影响使用。没有背景边类型时该分支不能假定存在；事件变化无法证明非实质时回到 `must_review`。`before_use` 在详情与所有 Handoff 中仍标“上游已变更未复核”，用于具体决定/行动或对外引用之前必须复核；不能借优先级降低自动放行。
3. `deferred`：仅用户点击“暂不处理”并写明非空理由、`triggerEventId`、目标 ID/版本、操作标识后成立。不能自动变为 `confirmed` 或写入覆盖关系；同一目标出现**新的** `triggerEventId` 时忽略旧暂缓、重新开放提醒，旧记录仍保留审计。持久化只增加这一类明确用户事件及必要兼容检验，不为派生优先级存储冗余值。没有经过安全迁移/恢复测试前不开放后台命令。

当 `Research.impacts` 仅展示同一根结论的一条代表路径、但 `contributingEdgeIds` 还包含其他贡献边时，不能由这条路径推断所有路径均安全；未能逐条核验时保守归类 `must_review`。直接必要边不得被另一条两跳路径隐藏。

分层函数必须确定性、无时间依赖、无模型调用，未知字段不降低安全层级。同一 `Research.impacts` 输出用于 flat（全部潜在影响待核对）与 tiered（相同集合按规则分组），不得用 G* 直接决定分层。离线重放须报告 `must_review` 对实质 G* 的召回、关键漏报、必须核对数量下降、落入 `before_use` 或 `deferred` 的实质目标数。关键漏报大于零：禁用分层、继续 flat；聚合视图可保留，但 pending/来源失效提示不可隐藏。数据不足则结果为 NEED_MORE_EVIDENCE。

## S3 组内显示与操作边界

- 按 `(projectId, triggerEventId, rootConclusionId, rootVersionId)` 聚合。例：“上游 X 已撤回，影响 8 项”。显示当前 `must_review`、`before_use`、显式暂缓的数量以及完整可展开清单；逐项审计事件照常写入，绝不把 8 条记录压成 1 条确认。
- “全部转使用前核对”只能对**当前已符合 before_use 规则**的项目执行；若包含任何 `must_review`，不得批量降级它们，界面必须提示哪些被保留。组内“逐项处理”保留逐项核查及明确确认边/事件的现有规则。
- 默认只展开一层后续传播；更深层显示“另有 N 项间接影响，使用前核对”，但后台保留完整影响集合，任何潜在 `must_review` 必须继续显式计数和阻断，不得因折叠变成安全放行。

## S4 复核结束

- 本次 Review 结束显示已覆盖的**具体事件、版本和目标集合**；剩余 N 项显示为待处理（按上方规则分层），不能把未核对项算入 `coveredChanges`。
- 提供“到此为止”，仅结束**本次复核任务/视图**，不把开放探索型课题自动设为 closed，也不消除必核对标记。
- 每次 Review 仅问一次“这次要拿去做决定或行动吗？”，默认“否”；选择“是”时所有 `before_use` 项必须在使用前核对；不因此自动结束探索或将偏好判断提升为事实核验。
- 复核与 Handoff 继续标注“上游已变更未复核”。按钮不能自动发送 ChatGPT 消息或自动重放不明操作。

## 与 Fork、徽标、试点的关系

- Fork 多分支结果属于同源采样；多次一致不能等同独立事实证据。对照页及 JSON 导出显示这一限制，不参与“依据充分”的判断。
- 现有工具栏徽标仍按版本过期的关联对话数计算。仅在 S3 分层及兼容测试完成后，才讨论将它另行变成“必须核对条数”。零态只能说明“无必须核对项”，不是所有研究事项已完成。
- 先完成独立真值、规则和输入映射冻结，运行 flat/tiered 离线对照并核实关键漏报为零，再评审 S3/S4 分组与收口实现。没有两人独立标注、案例记录或真实 F3 验收，不得把工程测试写成实际产品收益。

**不做：** DIVA 概率、效用矩阵、自动信息价值评分、以分支数量代替证据、将 Argdown 设为默认流程。
