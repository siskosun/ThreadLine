# ThreadLine 重建开发计划

**唯一正式计划：** 本文件。所有开发执行必须遵循仓库根目录 AGENTS.md。当前计划自 2026-11-01 起取代旧版 ThreadLine 课题管理、证据库、Fork 对照和 UI-D0–D3 开发路线。旧路线的提交、测试、PR 和验收记录保留为历史证据，不再作为新产品的开发任务或放行条件。

**本次基线：** 从 main 66879c56d07ca0995badd1ae097701efb4c58ecd 创建独立计划分支。当前 main 的正式 Release 仍为旧版 v0.8.2；本 PR 仅重写产品方向和治理计划，不表示新产品已实现、已安装或已发布。

## 1. 产品决策

重建为一个**纯浏览器扩展**，解决两个连续问题：

1. 将一个 ChatGPT 对话中的可见消息、分支、用户上传附件和助手生成文件，尽可能完整地保存到浏览器本地。
2. 在新建的 ChatGPT 普通对话中，使用本地保存的历史与用户选定的原始附件继续工作。

不再以旧 ThreadLine 的课题、证据、结论采纳、Fork 实验或研究图谱为核心。旧功能只有在新产品核心闭环完成后，出现明确用户需求并经过独立评估，才可重新立项。旧版本地数据不迁移，不为兼容旧 schema 保留架构。

**核心验收定义：** 原对话内容与文件真实落盘；浏览器重启后仍可恢复；新对话能取得接续历史及选定文件；文件上传状态可核验；整个过程不自动发送消息、不覆盖用户草稿、不删除源对话。

## 2. 开源基座与版本锁定

采用“保全基座 + 接续交互参考”的组合，不把 MoveChat 的 DOM 抓取层当作文件保全底座。

| 角色 | 项目与锁定版本 | 许可 | 用法与边界 |
| --- | --- | --- | --- |
| 主基座 | [ChatGPT Markdown Export](https://github.com/thekester/chatgpt-export)，v0.6.59，commit 13568bf75688de74a5af563b20d5ccd28f4ad532 | MIT | 复用对话 API 读取、附件/图片/沙盒文件解析、Markdown/JSON/ZIP、manifest、SHA-256、能力诊断及 Python 构建结构。 |
| 接续参考 | [MoveChat](https://github.com/VC067/MoveChat)，v1.2.1，commit c4fdb698c09c8be4fbe572ab8a7420bd1e0deb0f | MIT | 仅借鉴新聊天打开、短提示预填、DataTransfer/File 注入、平台适配和失败回退。不得照搬其空文件、DOM-only 文件采集或自动发送路径。 |
| 协议参考 | [pionxzh/chatgpt-exporter](https://github.com/pionxzh/chatgpt-exporter)，commit 6935bc1f9aba3a8767755d01fecaf31420f3bc19 | MIT | 重点参考最新 sediment:// 图像指针解析、缓存和相关回归测试；它是 userscript，不作为扩展主基座。 |
| 官方导出格式参考 | [OpenAI Export Parser](https://github.com/temnoon/openai_export_parser) | MIT | 只用于理解官方导出 ZIP 的多层归档、文件映射和历史格式差异；不引入本地常驻 HTTP 服务。 |

版本与仓库活跃度快照截至 2026-11-01：ChatGPT Markdown Export 最新发布 v0.6.59（2026-10-24）；MoveChat 最新发布 v1.2.1（2026-10-18）；pionxzh/chatgpt-exporter 最近更新于 2026-10-30。上游体量、提交频率和私有接口依赖均不足以支持无审查跟随更新。

**锁定规则：**
- Fork 后记录上游仓库、commit、版本、许可文件及本地改动；不自动跟随上游 main、不自动升级。
- 每次升级必须比较上游 diff、重新审查协议与权限，并运行本项目完整回归。
- 复制或实质改写第三方代码时保留对应版权、MIT 文本和文件级来源说明。
- ChatGPT Markdown Export 中“导出后删除对话”及其他删除对话的 UI、后台函数、请求路径和测试必须从分叉代码中彻底移除；不是仅隐藏按钮。新产品不申请、不调用删除对话接口。
- MoveChat 的自动发送选项和点击 Send 的代码必须删除；不能只将设置默认值改为 false。

## 3. 运行形态与总体架构

- Chrome / Edge Manifest V3 扩展；第一阶段以 Edge/Chromium 为真实验收目标。Firefox 仅在核心闭环稳定后评估。
- 无本地常驻程序、无本地 HTTP 服务、无云端后端、无第三方同步服务。构建工具只在开发阶段运行，不属于产品运行依赖。
- 运行时数据只保存在扩展自己的 IndexedDB。大文件以 Blob/分块字节保存，不将 Base64 当作长期存储格式。chrome.storage.local 仅保存小型设置和轻量索引，不存放整份附件。
- 用户主动导出的 ZIP 是可迁移、可独立保管的正式档案；IndexedDB 是便于浏览和接续的工作副本。UI 必须说明两者区别，不能把浏览器本地缓存说成永久备份。
- 对话读取、附件下载、文件注入均只在用户明确操作或明确开启单对话缓存后执行。认证信息仅在必要的页面内存中使用，不写入 IndexedDB、ZIP、日志或 GitHub。
- 默认不请求 <all_urls>。外部签名文件 URL 必须经过 HTTPS、主机白名单、重定向目标和大小检查；不得向外部文件主机转发 ChatGPT Cookie、Authorization 或 Referer。
- 不上传用户对话、附件、截图、导出 ZIP、Token、Cookie 或个人资料到公开 GitHub。自动化测试全部使用合成数据。

详细数据流和威胁边界见 [重建架构说明](architecture/REBUILD_ARCHITECTURE_20261101.md)。

## 4. 对话与附件保全要求

### 4.1 对话内容

- 从当前明确选定的 ChatGPT 对话读取原始可访问 JSON，保留原始数据副本、消息 ID、角色、时间、消息内容、可见工具结果、引用及附件关联。
- 保留 mapping / parent / children / current_node 等分支关系。主视图可优先展示当前分支，但归档不得把其他可访问分支静默压平或丢弃。
- 运行分支完整性检查：current_node 必须存在；父子关系必须可解释；检测循环、断链、重复消息 ID、不可达节点及消息顺序异常。失败时标记 partial/unknown，不得伪造完整。
- 仅保存用户可见的对话内容和明确可见的工具产物。不得导出隐藏的内部推理、系统提示或扩展不可见的内部数据。
- DOM 可作为可见性核对与降级来源，不能把只抓到当前渲染区域的 DOM 结果标记为完整历史。

### 4.2 文件与媒体

必须覆盖并分别记录：
- 用户上传的 PDF、Office、CSV、文本、压缩包、图片、音频及其他 ChatGPT 可见附件。
- 助手生成的代码解释器文件、图表和其他 sandbox: 产物。
- 图像和文件指针，包括 file-service://、sediment://、image_asset_pointer、file_asset_pointer、音频/视频指针、message metadata 附件和直接下载 URL。
- 文件引用所在的消息 ID、原文件名、MIME、大小、来源类型、下载时间、SHA-256、下载状态及失败原因。

**保存成功必须有实际字节。** 只识别到文件名、URL、asset pointer 或空 File 对象都不算文件已保存。任何失败必须写入 manifest 并在界面显示；不得用 0 字节文件、远端临时链接或虚构文件填充。

### 4.3 生成文件的过期风险

助手生成的沙盒文件可能在对话结束后失效。第三方资料关于数月后 HTTP 422 的说法尚未独立验证，因此计划不把固定过期时间当作事实；通过真实旧对话和不同年龄样本测量。

必须增加**单对话显式开启的实时缓存**：
- 用户在某个源对话中开启“自动缓存本对话新生成文件”后，扩展只监测该对话中新出现、可见且可归属的生成文件。
- 文件一旦出现即排队下载并写入 IndexedDB；同一文件按稳定指针去重，支持取消、失败重试的显式操作和断点恢复。
- 缓存开启状态、已缓存数量、待处理数量和失败数量持续可见；用户可随时停止。
- 不对所有 ChatGPT 标签页做全局静默抓取，不读取未选定对话，不把后台监测扩大为全量会话采集。
- 如果缓存开启前文件已过期、接口返回 403/404/422 或文件字节无法取得，标记为“远端文件不可恢复/未缓存”，保留证据，不制造空文件。
- 缓存能力依赖 ChatGPT 非公开接口，必须失败关闭并记录能力状态；不能承诺永久可取回。

## 5. 本地档案与完整性

### 5.1 IndexedDB 工作副本

建议按职责拆分 stores：对话/采集任务、原始消息页、分支关系、附件元数据、附件 Blob/分块、缓存队列和诊断状态。文件元数据与二进制分开；写入按事务和幂等键完成。

- 支持浏览器重启后继续读取、继续导出和继续接续。
- 使用 navigator.storage.estimate() 显示已用/可用空间；在用户明确操作时请求持久化存储能力，不能把浏览器持久化授权当作必然成功。
- 存储不足时停止新增写入并显示具体文件和失败阶段，不覆盖已保存文件。
- 缓存和导出支持取消；未知结果不自动重放。
- 允许用户删除本扩展自己的本地档案，但必须显示目标、数量和不可恢复范围；此功能与删除 ChatGPT 源对话完全分离。

### 5.2 ZIP 档案

一个对话的标准 ZIP 至少包含：
- conversation.json：原始可访问 JSON/分支数据及必要的规范化副本。
- conversation.md：便于阅读的完整对话记录，标明消息、分支、附件和来源。
- manifest.json：schema 版本、源对话标识摘要、导出时间、消息/分支计数、附件清单、完整性状态、失败记录和 SHA-256。
- assets/：已成功下载的实际二进制文件，按稳定 ID 或内容哈希命名，manifest 保留原文件名及消息关联。
- diagnostics.json：仅含脱敏的接口能力、错误类型和阶段，不包含对话正文、Token、Cookie、签名 URL 或原始文件内容。

大文件采用分块写入与 ZIP64/分卷方案；容量阈值由真实浏览器存储和构建测试确定，不沿用临时原型的 Base64 100MB/200MB 人为限制。任何被大小限制拦截的文件都必须明确标为未保存。

### 5.3 官方导出 ZIP 对照

真实验收必须加入 ChatGPT 官方导出 ZIP。第三方格式解析资料显示 2026 导出可能包含外层 ZIP、分卷的 Conversations/Files 内层 ZIP，以及 file-<ID>.dat；用户另有观察为 file_<id>.dat。命名存在来源/版本差异，**禁止把任一文件名形式写死为唯一格式**。

应先抽样读取实际官方 ZIP 的索引/映射，再按 message/file ID 将扩展归档与官方导出逐一匹配；对匹配文件比较 SHA-256，对无法匹配项分类为未出现在导出、格式未识别、接口不可用或内容不一致。官方导出也不能未经检查就当作所有助手生成文件的完整备份。

## 6. 新窗口接续要求

接续不能把 100 条历史消息原样塞进输入框，也不能默认重传所有附件。

生成一个接续包：
1. conversation_history.md：结构化、可检索的历史记录，包含对话目标、按时间排序的消息、分支标识、重要引用和附件索引。
2. handoff_prompt.md：短提示，只说明研究目标、当前进度、关键决策、尚未解决的问题、文件目录，并明确要求新对话先阅读历史附件。
3. 用户选择的原始附件：仅把本次任务真正需要的文件加入接续；其他文件留在本地档案，不自动上传。
4. handoff_manifest.json：记录源对话、归档版本、选中文件、缺失文件和接续状态。

**上下文限制：**
- 100 条或更长对话以历史附件承载，输入框只放短提示；不得把完整 transcript 直接粘贴进 composer。
- 附件数量上限不硬编码为 10。OpenAI [2026-02-13 发布说明](https://help.openai.com/en/articles/6825453-chatgpt-release-notes)曾称网页单条消息可附加 20 个文件；当前[文件上传帮助](https://help.openai.com/en/articles/8555545-uploading-files-and-audio-to-chatgpt)另列每 3 小时上传量和计划/项目差异。实际接续应读取当前网页控件并做真实测试，把 20 作为测试起点而非永久常量。
- 超出单条消息限制时，提供分批准备/上传流程；所有批次完成前不得提示“接续材料已完整”。不通过把 ZIP 强行当成 ChatGPT 一定能解析的文件来规避数量限制。
- 历史文件和附件即使显示在新对话中，也不等于模型已完整读取。接续验收要用历史早期、中间、末尾的已知事实进行检索验证。

**新聊天注入：**
- 只允许新建的普通 ChatGPT 对话；拒绝 Project、Temporary Chat、已有对话、未知跳转或非空 composer。
- 借鉴 MoveChat 的 DataTransfer/File 注入方式，但必须选择通用“Attach files”输入，不能误选相机/图片专用输入。
- 注入后观察 ChatGPT 页面真实上传状态。事件已派发、FileList 已设置或附件缩略图出现，都不能单独证明上传成功。
- 上传状态确认成功后交还控制权，由用户检查并手动发送。若页面无法确认，显示“上传状态未知”，不自动发送、不自动重试。
- 用户草稿、已选文件和已有页面内容绝不覆盖。若自动注入在有界时间内未能确认，释放自动流程并在侧栏显示一键文件暂存区：优先测试可拖拽文件条目；拖拽不受支持时提供下载接续包和人工上传入口。暂存区不得阻塞用户，也不得把未确认的文件标为已上传。
- 永不调用 Send、永不启用 autoSend、永不因静默超时推断发送成功。

## 7. UX 继承原则

继承并更新 DESIGN.md，保留研线已经形成的有效经验，但不继承旧产品的信息架构。

- 主路径只有三件事：保存当前对话、准备新对话接续、查找本地档案。低频设置、诊断和导出选项按需展开。
- 侧栏优先适配 360 CSS px，320px 仍可完成核心动作；长记录和档案详情使用宽页，阅读列最大约 960px。
- 保留原蓝灰、低噪音视觉方向、语义色、系统无衬线字体、8/12/16/24px 间距和 8/12/16px 圆角；不为了重建随意更换视觉体系。
- 每个任务区最多一个主操作；按钮使用“动作 + 对象”；避免不必要的副标题、重复标签、卡片套卡片和无信息量装饰。
- 当前源对话、完整/部分/未知、文件已保存/缺失、ZIP 已下载、新聊天已上传/未知、用户已发送等状态必须分开显示。不能把“保存”“导出”“上传”“发送”混成一个“完成”。
- 失败信息持续显示在相关操作附近，保留可恢复草稿；不只使用短暂 toast。缺失文件和上传未知必须显眼，不可藏进帮助说明。
- 遵守键盘可达、可见焦点、标签/错误关联、320px 重排和 WCAG 2.2 AA 目标；真人读屏和用户任务测试独立记录，不以 DOM 测试代替。
- 视觉及交互标准的具体目标、截图和验收矩阵见更新后的 DESIGN.md 与 [重建验收矩阵](acceptance/REBUILD_ACCEPTANCE_20261101.md)。

## 9. 验收原则

以下均为独立验收维度，不允许用合成测试替代真实网页，也不允许用“接口返回成功”替代实际文件可用性。

1. **采集完整性：** 100+ 消息、当前分支和可访问的替代分支；消息 ID、顺序、父子关系可复算；完整性状态准确。
2. **附件保全：** 至少覆盖 PDF、XLSX、CSV、PNG/JPEG、ZIP、用户上传文件和助手生成文件；每个成功文件有非零字节、正确 MIME/大小、SHA-256 和消息关联。
3. **实时沙盒缓存：** 真实生成文件出现后及时缓存；关闭缓存后不再读取；缓存前已过期的文件如实失败；旧对话样本记录 HTTP 状态及可恢复性。
4. **官方 ZIP 对照：** 使用同一账号可取得的官方导出 ZIP，匹配文件 ID/映射并比较哈希；不匹配项必须解释，不能只挑成功样本。
5. **重启恢复：** 关闭并重启 Edge 后，IndexedDB 档案、文件 Blob、manifest 和接续状态可恢复；损坏/空间不足时失败关闭。
6. **接续上下文：** 100 条以上历史不粘贴进输入框；新对话能够回答来自历史早期、中间和末尾的指定问题。
7. **文件注入：** 测试 1、10、20、21+ 文件；实际网页当前上限动态核实；超限时分批，缺失/失败不伪装成功。
8. **目标页安全：** 只允许新建普通聊天；非空草稿、已有聊天、Project、Temporary、未知 URL、页面切换均拒绝注入；自动发送次数必须为 0。

11. **发布：** 精确 HEAD 的 Linux/Windows CI、合成 Chromium MV3 E2E、真实 Edge 记录、第三方许可、ZIP 解压与 SHA-256 均核验。Beta/Release 仍需所有者单独授权。
