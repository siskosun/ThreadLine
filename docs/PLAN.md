### 状态与证据契约

- `planned`：尚未开始；创建空分支、生成计划、模型自评均不算执行完成。
- `in_progress`：已有具体代码和实验记录，仍未验收；不得因存在提交就标 `done`。
- `in_review`：已提交 PR 但尚未获得本任务的完整验收证据；PR 可以仍开放，也可能已合并，仍不等于本任务 `done`。被关闭而未合并的 PR 不能作为有效证据。
- `blocked`：需要在 `docs/ff/BLOCKED.md` 记录原因、解除条件和真实事实。
- `done`：提交 `docs/ff/evidence/<任务ID>.json`，由 CI 检查合并 PR 的真实状态、合并 SHA、测试用例和必要人工批准；子任务的依赖必须先 `done`。不允许拿 PR 自述、模拟网页或空白附件代替证据。
- `deferred`：当前未立项。第二期改为执行态必须经人工重新批准并修改本计划。
- 每次状态变更记录在 `docs/ff/PROGRESS.md`；实施阻塞写入 `docs/ff/BLOCKED.md`。其中的描述不覆盖本表状态。
- 数据与网页执行证据可以脱敏后记录于 `docs/ff/evidence/`；严禁存储 Token、Cookie、账号凭据及内部研究正文。
- CI 只能核查自动测试和公开 GitHub 证据。真人登录界面的验收仍须人在 PR 中确认，并留下脱敏的验收范围；自动检查无法替代人工真实操作。

## 一、结论与目标

以下第一、二期章节保留原方案及历史证据；日期对应当时状态。当前状态以上方机器表为准，下一阶段见第十一节。

在现有 ThreadLine 中扩展独立的「Fork 双分支对照（Beta）」，不重新开发浏览器工作台，也不引入桌面常驻服务、自定义 MCP 或自动发送。第一期完成可追溯的双聊天对照：冻结共同材料 W₀ 与指令 P、计算 SHA-256、创建两个独立空白会话并填入同一文本、用户人工发送、采集完整纯文本回复、显示去标签 X/Y 对照、记录用户裁决并导出自包含 JSON。

第一期**不实现自动 Flush、不自动提交消息、不自动重发、不运行 LLM 裁判、不提供 JSON 导入、不宣称验证 Fork-and-Flush 的因果收益**。功能入口默认关闭，原有 ThreadLine 课题管理与研究整理流程保持不变。

## 四、硬性架构与数据约束

1. **唯一写入者：** 扩展后台 `background.js` 承担实验状态变更入口；`ff.html` 只负责界面和发起操作。MV3 Service Worker 可暂停，任何关键进度都要持久化，并以操作幂等键和版本号防止重复写入。
2. **独立存储：** 新建 IndexedDB `threadline_ff_v1`，保留实验、A/B 分支、attempts[]、状态历史、捕获来源、裁决。原课题 schema、原备份格式、三天采集缓存不改变；第一期 JSON 可导出但**不可导入恢复**。
3. **权限最小化：** 独立 `FF_*` 消息接口，精准校验扩展页面来源、实验/分支/尝试/标签页归属。实验页面不得继承 `MUTATE`、任意备份或任意标签页采集权限；不得扩大 host permissions。
4. **实验隔离：** 两个新会话不得自动关联普通 ThreadLine 课题，不继承课题同步或收口拦截。默认仅支持非 Project 的普通新聊天；不以 Temporary Chat 为已支持路径。
5. **输入及输出安全：** W₀/P、采集回复通过 `textContent` 等安全纯文本方法展示，不执行其中的 HTML/脚本；导出与日志不得含 Cookie、Token、认证头。现有采集器读取同源授权头的事实应如实记录，不能声称链路完全不接触凭据。
6. **人工隔离确认：** 记忆、引用聊天历史、两边自定义指令、模型、思考强度、工具配置和项目归属分别记录 `yes/no/unknown`，并记录人工确认时间。人工确认不等于已验证服务端隔离。第一期不宣称受控因果实验。
7. **长度限制：** 冻结的最终发送文本不超过 24,000 UTF-8 字节，拒绝而非静默截断。必须验证 ProseMirror 编辑器在近上限长度、中文、emoji、代码块和换行情况下的实际填入/回读。

## 五、输入一致性契约

冻结 W₀ 与 P 后，按固定模板组合**同一份**最终发送文本，分别保存冻结原文和 SHA-256。规范化规则版本固定为 `canonicalization-v1`：

- `frozen_hash`：移除开头 BOM，将 CRLF/CR 改为 LF；**不**修剪首尾空白、**不**合并内部连续空格、**不**删除 Markdown 或代码缩进。
- `compare_hash`：基于上述文本，再将 NBSP 变为普通空格，并修剪整段首尾空白；内部空格与换行不变。
- 用户实际发送的消息应从可信完整的来源读取，不能把已经经过 `trim()` 的有损采集投影宣称为逐字一致。网页渲染或 Markdown 自动转义导致的等价关系必须经针对性测试确认，不能任意放宽。

四级比较：`exact`（可信来源完全一致）、`canonical_equivalent`（按已冻结规则一致）、`unverified`（文本源不可信或不完整）、`differs`（有实证的输入差异）。仅前两级允许完成判定；`unverified` 对应 `unknown`，`differs` 对应失败/排除。分别比对 A/冻结、B/冻结及 A/B 两两一致性，持久保存原始哈希、比较哈希、规则版本及来源说明。

## 六、完成与失败状态契约

四种主状态：`pending`、`done`、`failed`、`unknown`。用附加执行阶段标明 `created`、`draft_ready`、`awaiting_send`、`generating`、`capturing`；每次转换写入时间、原因、尝试 ID 与证据。

只有**同一会话 ID**、**输入一致性合格**、**确认只有一次用户任务**、**对应的最终纯文本回复完整**、**生成结束有至少两类可检查的信号**、**数据已成功保存**，才能将该分支标记为 `done`。`captureComplete=false`、旧版采集回退、文本截断、工具/非文本内容无法抽取、重新生成、额外追问、会话身份冲突均不得自动认定成功。

可用信号包括页面从生成转为结束、最后回复稳定不少于 5 秒、以及会话数据中的可信结束标记。停止按钮消失或固定等待时长**不能单独证明完成**。

未知是否发送、发送后丢失回执、浏览器关闭/重启、页面结构变化、限流状态无法确定等，一律 `unknown`，**不得自动重发**；人工新运行使用新 attempt ID，不覆盖先前失败记录。双分支只有两个指定 attempt 均 `done` 才能进入正式对照。

### 4. 用户主流程与界面

1. 在现有整理结果或已揭盲 Fork 结果中选择“采纳”；默认只确认正文和依据，适用条件按需填写。可以同时采纳不同分支的内容。
2. 回到课题后直接阅读结论；“依据”紧邻文字，展开后显示证据片段、来源类型、原文位置及采集范围。来源不可定位时仍可查看已保存片段，并明确说明限制。
3. 只有需要时打开“依赖”，记录必要前提并确认关系；默认折叠显示前三条，可继续添加，无三条业务上限。不强制每条结论建关系；未记录不等于没有依赖。
4. 生成接续材料时预览新增、更正、撤回和待核对项目，再编辑、复制或使用既有人工预填。复制、预填、人工确认看过、模型已理解是不同事实。
5. 后续试点通过后，才在真正发生变化时显示待核对数量；打开某项只展示相关上游、下游及证据，需要时展开一层局部关系。

主界面保留当前课题、已采纳结论、待核对变化和继续研究入口。备份、版本历史、技术诊断按需展开。避免重复标题、装饰徽标和与标题同义的说明；用布局表达层级。保留不完整来源、冲突、未知状态与外发范围等影响用户判断的信息。

### 5. 分阶段数据契约

S1 只持久化已采纳/已撤回结论及其证据，候选仍使用现有整理记录；不要求用户填写事实/推断/假设类型。核验结果与依赖在 S2/S4 增量加入，缺省表示未记录，不能解释为“已核验”或“没有依赖”。新增普通字段可以不改变 IndexedDB store 结构，但仍须更新数据验证、备份格式兼容和缺省读取；新增 store/index 则另行升级。

| 记录 / 引入阶段 | 必要字段与不变量 |
| --- | --- |
| Conclusion / ConclusionVersion，S1 | 稳定结论 ID、projectId、不可变版本 ID、正文、可选适用条件、adopted/withdrawn、前版本、创建者/时间与 changeType；修改创建版本，撤回保留历史 |
| SourceSnapshot，S1 | 来源 ID、类型、可用 URL/会话/消息/页码、选区及上下文、原文哈希、采集时间、片段范围与采集完整性；模型消息不冒充外部资料，哈希不证明真伪 |
| EvidenceLink，S1 | 结论版本到来源片段的连接；关系缺省为“引用”，用户可标支持/反对/背景但不强制；来源编号绑定采集运行，禁止跨运行误用 M1 |
| Dependency，S2 | 稳定 edgeId、projectId、upstreamConclusionId、downstreamConclusionId、必要前提类型、edgeRevision、active/removed；不因正文改版新建边；有效确认由下述版本指针及事件历史表达 |
| DependencyConfirmation，S2 | edgeId、acknowledgedUpstreamVersion、confirmedForDownstreamVersion、材料快照哈希、操作人/时间、理由及事件 ID；不可变历史，当前指针只来自有效确认 |
| Review，S4 | 目标结论/依赖、准确上下游版本、结果、scopeManifestHash、材料哈希、分支/attempt、理由和人工决定；scope manifest 列出核对的问题、范围、条件、来源 ID/哈希和缺失项 |
| Handoff，S1 | 已提交结论版本及撤回/缺证差异、必要证据和已知未知项、材料哈希；复制、人工看过、模型已理解分开，不由 seenVersion 推断接收 |

**依赖版本规则：** 边连接稳定结论 ID，确认钉住上下游版本对。一个上游版本指针不足以证明新下游正文仍依赖同样的前提。S2 即冻结以下规则，S3 使用同一协议计算提醒。

| 事件 | 边、确认与提醒的处理 |
| --- | --- |
| 下游 v3 改为 v4 | 保留同一 edgeId 与确认历史；默认“实质修改”，把关系适用范围标为待重确认。旧上游指针不自动变新，旧待核对原因不删除 |
| 用户明确选择“仅措辞” | 未改适用条件/来源连接，且当场确认依赖继续适用时，追加 carry-forward 事件，更新 confirmedForDownstreamVersion；上游指针原样继承。若上游已变更，仍保持待核对；这是用户判断，不是系统语义证明 |
| 上游 v2 升到 v3 | 新建或归并影响事件，记录旧确认版本与当前版本；去重键包含 edgeId、triggerEventId、targetDownstreamVersion。一个事件多路径到达只显示一项，保留所有原因 |
| 已对照上游 v3 核对下游 v4 | 在同一事务写 Review/Confirmation、推进两个指针并关闭对应触发原因；关闭一个原因不清除其他上游或来源的提醒 |
| 复核时上游又变 v4，或下游又变 v5 | 旧复核仅入历史并标 stale；不推进当前有效指针、不清理新提醒，要求基于新快照继续 |
| 删除依赖或撤回结论 | 追加显式事件和理由；历史不消失。删除边只关闭其关系范围内的当前提醒，保留审计；不删除下游正文，不宣告其为真/假 |

必要前提图按稳定 ID 拒绝自环及环。实质改写后尚未重确认的旧边仍作为“关系适用性待确认”参与保守影响候选，并显示原因，不能靠改版本让潜在影响消失。算法测试的已登记图闭包正确性与产品层面登记完整率分别验收。

**复核结果映射：** Review 的 scopeManifestHash 绑定范围清单，材料哈希本身不能表达“核对了什么”。没有核验记录默认 unverified；reviewNeeded 是独立的新鲜度提示。

| 人工复核结果 | 结论/核验状态与指针 |
| --- | --- |
| 保留 | 目标版本仍 adopted；仅对已完成核对的 scope 记 confirmed；有明确确认的依赖推进版本指针 |
| 修订 | 创建新的 adopted 版本，旧版本保留；新版本默认 unverified，只有另有针对它的明确核验事件才记 confirmed；相关依赖重新确认 |
| 撤回 | withdrawn；不自动记成“错误已证明”，事实反证可另记 disputed；上游撤回的下游影响仍需处理 |
| 无法判断 | 不改变采纳状态，记 inconclusive 的 Review，当前范围仍 unverified；若先前存在 confirmed，仅保留其历史范围，reviewNeeded 不清除 |

disputed 需要人工明确记录反证/冲突，不能由“修订”或“无法判断”自动推出。后续新范围核验不会覆盖旧范围记录。

### 6. 存储与恢复

**权威方向：evidence IndexedDB → chrome.storage 兼容投影。** 关联稳定课题 ID，旧 schema 2 暂不强制迁移；课题名称等原有字段仍由旧课题库管理。证据结论正文以新库为唯一权威。

1. 新库在一个 `readwrite` 事务内提交 Conclusion、Version、SourceSnapshot、EvidenceLink、project evidenceRevision、operationId 及投影待办；事务 `oncomplete` 才确认保存。哈希/模型/文件读取在事务前完成，事务内不跨网络或其他异步等待。
2. 复用 `background.js` 的消息入口和排队模式，由 service worker 唯一执行证据写入；面板只发命令。持久正确性由同事务内 revision CAS、唯一操作 ID 和请求摘要保障，不能依赖 worker 内存队列活着。相同 operationId/摘要返回原结果，不同摘要拒绝；CAS 冲突提示重新审阅。
3. 向 chrome.storage 的投影只从已提交权威库重算，携带 projectionRevision；通过同一后台队列串行写入，并在写前后复查最新 evidenceRevision。中断后的投影待办持久保留，启动/读取时幂等重算；不反向读取 decision 更新证据。恢复只重算本地派生数据，不重放采集、模型请求、发送等外部操作。
4. 事务成功而投影失败显示“已保存，摘要待更新”；只从 IDB 读取的结论视图可继续使用。所有交接读取一致的权威快照；旧投影、丢失权威库或 revision 不匹配时，旧入口不得冒充最新结论。证据库缺失须明确报错，不能以空库重建覆盖兼容摘要。
5. 首次采纳后，旧 decision 变为只读摘要；后台消息处理也拒绝该课题的直接 decision 修改，不能只禁用按钮。无证据库接管记录的旧课题沿用旧编辑方式；转换时保留原文为 legacy-note（未验证），不悄悄变成有证据结论。课题一旦接管，即使全部撤回也不自动恢复双向编辑。
6. 旧备份恢复、撤销、批量更新、直接 MUTATE 与已打开的旧面板均须遵守同一规则。课题删除和名称恢复与证据库存在的跨库关系另用后台串行、持久意图/墓碑与幂等对账；这不是与结论正文的双向合并。S0 输出崩溃点表及恢复顺序后才能进入 S1a；未定义的破坏性路径在已接管课题上拒绝执行。

旧 decision 的 1,000 字符上限仍保留，只输出明确标注截断的摘要；完整结论通过新 UI 与交接读取。统一迁移原课题 schema 是备选，不在本轮默认实施。存储协议来自已有 `ff-db.js` 的事务/CAS经验，但需新的多 store、配额失败及重启测试，不能把旧测试覆盖当作新实现证明。[IndexedDB 事务说明](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API/Using_IndexedDB)与 [MV3 生命周期](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle)为约束来源。

**S0 需验证并冻结的首期默认值：** 数字为产品试点限制，不是浏览器配额保证。结论正文最多 4,000 Unicode code points；单条证据默认选区加前后各最多 500 code points 上下文，总计不超过 16 KiB UTF-8，超限让用户缩小选区或显式调整，不能静默截断。每条结论最多 8 个片段、总计 64 KiB；单课题最多 200 个稳定结论、每结论最多 50 个版本，达到上限提示导出/清理而不自动淘汰。单个导入/导出包最多 20 MiB 未压缩 UTF-8 JSON；全库由用户可见的 100 MiB 产品预算限制，包含历史/快照/待办，按字节计数且实际配额失败仍需处理。大库按课题导出，单课题超限须明示不能完整导出，禁止静默裁切；S0 验证峰值内存与生成/恢复耗时后调整这些默认值，改动应留理由并在 S1a 前冻结。

备份从首个持久化版本起覆盖证据、历史和引用，导出前明确“包含对话原文片段”，提供课题/内容范围预览。脱敏删掉证据的导出必须标为不完整分享包，不能假冒可完整恢复的备份。导入先限字节、验格式/哈希/引用、预览条数与原文范围；损坏、未来版本、ID 冲突和跨课题引用拒绝或要求明确处理，不静默覆盖。旧格式只恢复它包含的内容，不清空新库。

“撤回”保留研究历史；明确删除时清理扩展管理的对应原文及副本，必要墓碑不保留正文，已导出的外部文件无法收回。首次采纳成功后显示一次简短导出备份提示，并保留可发现的备份入口。外发模型沿用现有用户选择与确认，默认不新增上传。

Chrome 官方说明：清除浏览数据一般不清除扩展 origin 的 IndexedDB；默认仍有配额及少见的存储淘汰风险，可查询 estimate/persisted 并考虑 persist。当前 manifest 没有 unlimitedStorage；本轮不默认加权限，persist 是否获批不能预设。卸载、显式清库/删除配置文件等另行验证；S0 只用一次性合成配置，不触碰用户实际数据。[扩展存储文档](https://developer.chrome.com/docs/extensions/develop/concepts/storage-and-cookies)

### 9. 试点与投资门槛

以下数字是 ROOT 提出的预注册门槛，不是已测收益。试点开始前将案例、真值、指标、阈值、操作日志方案和协议哈希冻结；查看工具输出后不能调整阈值来宣称通过。若设计改变，保留原失败/未知结果，另开后续试点。

**案例与独立性：** 6 个脱敏案例，每例 5–10 条重要结论，覆盖口径变化、前提撤回、来源丢失、仅措辞和无关分支。预先标注必要前提集合 E*、变更事件、每事件应受影响集合 G*、关键漏报集合；标注者先不看工具输出。至少 2 个案例由第二人独立标注，分歧在跑工具前裁定并保存。无法获得第二人时只能报告探索结果，不能放行 S3。报告超过 3 个真实必要前提的结论数/占比及漏登记依赖；“先显示 3 条”只是界面折叠，没有业务上限。

**S2 提前测收益：** 离线脚本读取冻结的人工登记边 E，按已定义版本/确认规则算候选影响集合 P，和独立的 G* 对比；不得从 E 自动生成地面真值。脚本无 UI、无模型调用、无网页操作，输出版本、输入哈希、逐例 TP/FP/FN 与遗漏路径。S3 复用该纯逻辑和用例，避免再次实现传播算法。离线结果验证潜在价值，不宣称生产提醒已有效。

影响集合以（案例、变更事件、下游结论 ID/版本）去重；TP/FP/FN 先跨案例累加计算 micro 比率，同时披露逐例结果。登记完整率比较的是冻结时点的直接必要前提，不用传递边增加分子。原型 P90 使用 nearest-rank；耗时中位数口径在冻结协议中保持一致。

| 指标 | 定义及预设门槛 |
| --- | --- |
| 依赖登记完整率 | 经真值匹配的已登记必要前提数 / 真值必要前提总数（所有案例 micro 汇总）≥90%；关键必要前提 100%；错误登记不能进入分子 |
| 潜在影响召回率 | TP/(TP+FN) ≥90%，非空 G* 的每例 ≥80%，关键漏报为 0；包括因未登记关系造成的漏报 |
| 潜在提醒精确率 | TP/(TP+FP) ≥80%；空 G* 案例不得有 FP；没有预测且真值非空视为召回 0，精确率 N/A；两者皆空单列正确无影响，不给满分抬高均值 |
| 正确接续总耗时 | 按同案例配对，(基线耗时−候选耗时)/基线耗时 的中位数 ≥15%，且至少 4/6 案例不慢于基线；未正确完成的案例计失败，不能剔除 |
| 工程硬门槛 | 确定性夹具中已登记图漏算、错误来源匹配、静默覆盖/数据丢失、自动发送均为 0；这是算法/安全要求，独立于上述产品完整率 |

当前研线与候选功能必须配对比较，交叉安排使用顺序；Arguma 可作为补充，不可用记未执行。耗时来自操作日志，包含首次采纳/登记、维护、更正、对照离线影响清单、复核误报及生成正确交接；工具学习时间另列并报告含学习成本的敏感性结果。需要纠正才能达到真值的步骤全部计时；日志不记录研究原文。用户愿意再用是定性信息，不单独放行，也不替代第二人标注。

任一硬门槛不通过则修复后重新验证；产品阈值未达标则保留 S1、简化或停止依赖功能。样本不足、第二人缺失、日志缺失或真值仍有实质争议记 NEED_MORE_EVIDENCE。不得用小样本通过宣称普遍或因果收益。

本次调研中的评分、更名、论文和具体 Issue 故障率没有逐项复证，不作为投资效果证据。当前计划采纳记录见 [评审处置](ff/PLAN_ADOPTION_20261024.md)；其事实、建议与尚未执行的试点/小样分别列示。

以 [UI_AUDIT_20261025.md](https://github.com/siskosun/ThreadLine/blob/78d37950ea0eaace17e15a8e4aad31c2db787eed/docs/ff/UI_AUDIT_20261025.md) 已实现的三主导航、响应式布局、表单和回包/草稿隔离为基线。不重复立项这些代码。

真实用户任务包括：首次采纳并核对原文、从提醒进入局部复核、对照版本与完成交接；逐项记录**无人帮助任务成功率、错误操作、放弃/恢复、总耗时和第二次自然复用**。保持上方 S0A 既有 12 次有效采纳、至少 11 次无人帮助、耗时中位 ≤30 秒/P90 ≤60 秒及至少 4 次非设计者操作等历史口径；如缺真实证据，记未知，而不是以自动点击时间替代。

只针对观察到的失败改 UI。高级图谱、Argdown、JSON 和完整历史继续按需展开。

### 12.6 可行性筛选 `threadline-s2-pilot/2`（新增协议，不覆写 /1）

**目的：** 检验完整候选相对现有工作流与“新对话直接重做”的增量价值。此阶段为 **feasibility screen（可行性筛选）**，不能因小样本达标就宣称产品效果已被确认。

**三臂设计：**

- **A**：现有 S1 证据与交接，不启用 S2–S4 依赖提醒。
- **B**：S1 加候选 S2–S4 依赖、变化提醒与局部复核。
- **C**：新对话中给模型同样原始资料、约束和问题，直接重新完成研究；完整计入模型调用成本、人工核查及修正。三个臂同等可见原始资料，记录模型版本和预算；不同自然流程允许存在，但不得悄悄改变研究问题。

**样本与冻结：** 最初 6 个独立脱敏案例，每例 5–10 条关键结论、至少 5 个预定义变化事件，合计 ≥30 个事件；涵盖前提错误、口径调整、来源丢失、纯措辞和无关分支。先冻结正确必要边 E*、每事件真实影响集合 G*、关键漏报、比较臂、操作顺序、日志字段、排除条件、协议 SHA-256；工具结果不能反向生成真值。至少 2 个案例独立双人标注并在执行前解决分歧，否则仅作探索性分析。交叉安排顺序，记录操作者先前见过答案所造成的学习污染。

**统计口径：** 事件作为观察单位，但同一案例的事件并不独立；公布每例和每事件 TP/FP/FN/正确性/耗时，按案例进行聚类敏感性分析与不确定性报告，区分事件级描述、案例级对比和案例内依赖；不能把 30 事件作为 30 个独立案例计算置信区间。包括失败、放弃、未执行与反向误改，并同时报告学习成本计入/不计入的耗时。对 A/B/C 做配对比较，主要关注**正确接续率、误改率、实际耗时、人工补救与成本**。

**原历史门槛降格为投资筛选参考：** 必要边登记 ≥90%、关键边漏登 0、潜在影响召回 ≥90%、精确率 ≥80%、关键漏报 0、B 对 A 中位总耗时改善 ≥15%、至少 4/6 案例不慢于基线。这些是第十一节既有筛选数字，**不是总体性能达到阈值的统计证明**。对照 C 可以证伪“定向复核优于重新生成”的主张，不能预设 B 更好。

**工程硬门槛不降低：** 确定性夹具已登记图漏算、错误来源匹配、静默覆盖/丢失、未授权自动发送均为 0；这与研究统计效力无关。旧 `threadline-s2-pilot/1` 的冻结输入和输出继续可复算，不修改其阈值或历史日志；新增 `/2` 协议/评估器须独立实现和验收。

**筛选后的动作：** 积极信号仅支持追加独立案例开展确认性研究，不直接宣称因果或推广结论。无明显改善或维护成本高于收益时保留 S1，停止继续扩张 S2–S5；研究质量下降时优先找出误报/误改机制，再决定禁用或移除。

### 12.6.1 pilot/2 预冻结修订（2026-10-26，尚未执行）

**先修订、后冻结、再运行。** 本修订与 [分层规则规格](ff/S3_TIERING_PRESPEC_20261026.md) 必须在首个 `threadline-s2-pilot/2` 协议字节 SHA-256 登记之前完成；`freeze.commitSha` 应记录已存在的前置输入/规则提交，不可自引用未来保存冻结协议的提交。冻结文件提交后，将最终协议 SHA-256 与存储提交 SHA 另行登记，原文件不回写；冻结后任何口径变更均另起版本和独立案例，不按观测结果回写已有规则。原 `threadline-s2-pilot/1` 的冻结输入、结果和阈值原样保留。当前仅有协议与评估器候选 [PR #45](https://github.com/siskosun/ThreadLine/pull/45)，`NOT_EXECUTED`；B 臂必须在独立测试通过后采用分层候选，绝不能把 flat 与 tiered 混合记为同一版 B。

**真值单位：** 对每个（案例、触发事件、下游结论）冻结影响集合 G*，并为 G* 的每个成员预标 `substantive`（实质）或 `non_substantive`（非实质）。不在 G* 内的预测候选是误报，不得为方便计算伪造一个“非实质 G*”来扩充真值。关键错误另按事件/受影响目标冻结，不随预测调整；全部六案例各保留至少一份原始标注的 SHA-256 收据，至少两案例由两人分别提交独立原始标注哈希，并记录冻结前的 `adjudication` 分歧裁定收据与时间。程序只能检查格式及提交先后，真实独立性仍须人工核对原始文件。分层规则及输入映射须由看不到试点预测/评分结果的人员先冻结；如果已看过真值再调规则，只能报告探索性筛选。

**三项增量指标（不增加第四臂）：** （1）无实质影响复核耗时：凭可追溯到目标结论的人工操作日志，汇总复核 `non_substantive` 真值目标和误报目标的时间，分别报告含/不含学习成本、占全部可归因复核时间的比例及无法归因的剩余时间；不能用总体耗时减去“成功耗时”倒推。（2）重要错误捕获并纠正率：实质 G* 中最终交接经独立人工核对为正确的（事件、目标）个数 / 实质 G* 总数，A/B/C 每案例报告后再做案例聚类描述，不把仅被提醒当作已纠正。（3）必须核对负担：按每事件及每案例记录 `must_review` 条数，并同时公布 `before_use`、用户明确暂不处理的条数和原始 flat 条数。三项均要求日志/材料可验，缺失记录为 `NOT_EXECUTED`，不得以 0 填充。

**同一冻结 E*/G* 离线重放：** 直接使用现有 `Research.impacts` 计算 flat 的全体潜在影响，同一预测集合再由冻结的纯规则派生 tiered（`must_review / before_use`），不使用 G* 反向生成预测；`Research.impacts` 的单条代表路径可能遗漏其他贡献路径的风险，若 `contributingEdgeIds` 存在无法独立核验的其他边则保守保持 `must_review`；用户明确暂不处理需有事件、理由与操作收据，其结果另报，不作为事前模型预测。分别报告必须核对层对实质 G* 的召回（既有筛选参考 ≥90%）、关键漏报数（上线硬门槛 0）、相对 flat 的必须核对条数下降率，以及流向 `before_use` / `deferred` 的实质真值（事件、目标）个数。对同一案例内事件不假定独立；输出逐事件、逐案例及案例聚类不确定性。**关键漏报非零时不启用分层，回退 flat；聚合显示可以保留，但任何安全待核对标记不能隐藏。**

**不必要复核负担预注册对照：** 在 A、B 两臂使用相同操作日志分类规则，比较无实质影响复核时长占可归因复核时长的比例；预注册采用每案例 B−A 的无实质复核占比差值中位数 ≤0 作为筛选参考，并给出案例聚类描述；任一案例缺少学习时间归因则比较记为未知，不凭空设置绝对分钟数，也不将无样本的比例当零。若 B 的正确接续不优于 A，或原有中位总耗时改善未达 15%，停止 S2–S5 扩张、保留 S1；六案例只支持可行性筛选。

**实施顺序不变：** #36/S1 安全修复及切片、F3 真实采集继续作为主线；本节的规格、Fork 同源采样标注和离线评估可独立推进；按本规则与冻结真值完成离线重放并证实关键漏报为 0，才评审 S3 的提醒分组/收口交互。S3–S4 UI 在此门禁之前仍为独立 Draft，不得改写成已验收。正式计划状态、版本/发布审批及原有真人门禁不因协议修订自动变化。

### 12.8 已实现功能增量与平台风险

S4 已支持祖先范围冻结、旧参考查看、四种复核结论、过期历史及交接更新，后续 D 类工作**只针对已出现的缺陷**（例如交接遗漏变化、旧分支仍用旧前提、来源定位失败、提醒入口过于繁琐）。不得重做已完成机制。

每次发布前检查 ChatGPT 原生项目/引用/版本功能是否已直接覆盖研线的核心任务，并在隔离配置运行 DOM/选择器兼容测试。若站点变更导致网页采集不可用，降级到片段、原始链接与人工导入，不伪称定位成功、不自动重试网页写入。保留完整 JSON 备份及已有 Argdown 互通作为迁移基础；跨 Claude/Gemini 平台适配暂不立项，除非有明确实际需求和投入收益。
